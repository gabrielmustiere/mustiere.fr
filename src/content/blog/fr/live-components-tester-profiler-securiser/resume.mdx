Trois objections de code review reviennent toujours sur Live Components : tester, profiler, sécuriser. Toutes ont des réponses précises sans outillage nouveau,
parce qu'**un Live Component, c'est un contrôleur Symfony déguisé**. **Tester** : trait `InteractsWithLiveComponents` en `KernelTestCase`, API `set` /
`call` / `refresh` / `emit` / `component()` / `render()` qui couvre 90 % des cas, pas de Panther ni jsdom. **Profiler** : le profiler Symfony intercepte les
`POST /_components/*` comme n'importe quelle requête — onglets Doctrine (queries / cycle), Twig (rendu), Performance. À chercher en premier sur un composant
qui rame : un N+1 lazy invisible au render initial mais rejoué à chaque cycle Ajax. **Trois pièges perf** : entité Doctrine entière dans une `LiveProp` (fix :
`hydrateWith` / `dehydrateWith`, sérialiser l'ID), même méthode appelée N fois dans un template (fix : `computed.foo`), `data-model` sans `debounce` sur input
texte (fix : `debounce(300)|query`). **Sécuriser** : l'état voyage dans le DOM, donc **jamais de secret dans une `LiveProp`** — c'est la seule règle propre au
bundle. Le reste est du réflexe Symfony : `#[IsGranted]` sur les `LiveAction`, `writable: false` par défaut, validation des `LiveProp writable` comme une entrée
utilisateur, `writable: ['name', 'email']` (whitelist explicite) sur les DTOs. **Latence** : 30-80 ms en dev local, 80-200 ms en prod même région, 200-500 ms en
4G, 500 ms-2 s en réseau dégradé. Pour 95 % des UIs CRUD, c'est acceptable. La règle de décision en review est dans l'épisode 5.
