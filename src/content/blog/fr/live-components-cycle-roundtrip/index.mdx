C'est le pivot de la série. Les épisodes [1](/blog/symfony-avant-ux-inventaire/) et [2](/blog/twig-components-socle-statique/) ont posé le diagnostic et le
socle statique. Cet épisode attaque la moitié _réactive_ du modèle. Live Components est une **surcouche** de Twig Components — pas un remplacement. Tout ce
qu'on a vu à l'épisode 2 reste vrai. On ajoute une couche de réactivité quand on en a besoin, composant par composant. C'est de l'opt-in. Un Twig Component
devient Live au prix d'une annotation et de quelques attributs sur les props ; le reste de la classe ne change pas.

## Une famille, pas un OVNI : HTML-over-the-wire

Live Components ne sort pas de nulle part. Il s'inscrit dans une famille d'approches émergée entre 2018 et 2022, qu'on regroupe sous l'étiquette
_HTML-over-the-wire_ ou _server-driven UI_. L'idée commune : l'état de vérité vit côté serveur, le client n'en est qu'une projection, et on échange du **HTML**
plutôt que du JSON.

| Solution                                                  | Stack              | Année | Idée centrale                         |
| --------------------------------------------------------- | ------------------ | ----- | ------------------------------------- |
| [Phoenix LiveView](https://hexdocs.pm/phoenix_live_view/) | Elixir             | 2018  | État serveur, diffs via WebSocket     |
| [Hotwire / Turbo](https://hotwired.dev/)                  | Rails (agnostique) | 2020  | Turbo Frames + Turbo Streams          |
| [Laravel Livewire](https://livewire.laravel.com/)         | PHP / Laravel      | 2020  | Composant PHP réactif, requête HTTP   |
| [htmx](https://htmx.org/)                                 | Agnostique         | 2020  | Attributs HTML → fragments serveur    |
| **Symfony UX Live Components**                            | PHP / Symfony      | 2022  | Modèle Livewire-like, idiomes Symfony |

Cette famille assume des choix qui sont des disqualifications dans certains contextes : un round-trip HTTP par interaction (ce qui exclut le offline et les
animations 60 fps), une dépendance au réseau (ce qui ferme le terrain canvas, drag & drop temps réel, éditeurs collaboratifs), un modèle où l'état riche côté
client est volontairement absent. Ce qu'elle gagne en échange : pas de double codebase, pas d'hydratation coûteuse, pas d'écosystème JS séparé à maintenir, et
un SEO trivial parce qu'on rend du HTML.

## Stimulus dans l'image — intégré, pas remplacé

Avant de regarder les briques, il faut nommer ce qui s'exécute côté navigateur. Live Components s'appuie sur un **contrôleur Stimulus** côté client, packagé
dans le bundle (`live_controller.js`, environ 25 à 30 Ko en production sur la version actuelle). On n'écrit pas de JavaScript, mais on en exécute. Cette
dépendance n'est pas un détail à cacher.

Concrètement, le bundle livre des contrôleurs Stimulus qui s'enregistrent **automatiquement** côté client via le _Stimulus bridge_ : un
`composer require symfony/ux-live-component`, le bundle expose son contrôleur JS, Symfony Flex écrit la déclaration dans `assets/controllers.json`, AssetMapper
lit le fichier, et `data-controller="live"` est disponible partout. Zéro `npm install`, zéro config Webpack, zéro Vite — la pipeline d'assets de Symfony suffit.

Ce qui devient redondant n'est pas Stimulus. C'est le couple _Stimulus custom + endpoint Ajax custom_ pour faire de la réactivité serveur. Stimulus reste
l'outil de choix pour tout comportement 100 % client, et on retrouvera cette règle à l'épisode 5.

## Trois briques : un état, un verbe, une liaison

Un Live Component, c'est un Twig Component augmenté de trois briques.

`LiveProp` est l'**état** : une propriété PHP synchronisée entre le client et le serveur. Elle se sérialise dans le DOM au render initial, revient dans chaque
payload, et rejoue le rendu côté serveur. `LiveAction` est le **verbe** : une méthode PHP déclenchable depuis le DOM. Pas de route à déclarer, l'autowiring
fonctionne comme sur un contrôleur classique, le CSRF est géré par le bundle. `data-model` est la **liaison** : un attribut Twig qui lie un input à une
`LiveProp` et déclenche un re-render — l'équivalent direct du `v-model` de Vue.

## Le cycle en deux phases

C'est le moteur. Tout le reste découle de ça.

**Phase 1 — render initial (une fois).** Le navigateur fait un `GET` sur la page. Côté serveur, Symfony instancie le composant, Twig le rend, le bundle
**sérialise l'état** (les `LiveProp`) dans le HTML rendu — sous forme d'attributs `data-live-*` sur l'élément racine — et renvoie tout ça. Le composant n'existe
plus côté serveur après ça. Son état est encodé dans le HTML que le navigateur a reçu.

**Phase 2 — cycle interaction (à chaque action).** L'utilisateur clique ou tape. Le contrôleur Stimulus côté client lit l'état sérialisé dans le DOM, le
recompose, et fait un `POST /_components/<NomDuComposant>?action=<methode>`. Côté serveur, le composant est **reconstruit** à partir de l'état envoyé, la
`LiveAction` est exécutée, Twig re-rend le composant, et le bundle renvoie le HTML partiel. Côté client, **morphdom** (ou Idiomorph dans les versions récentes)
applique un diff ciblé sur le DOM — il ne remplace pas le markup, il patche **uniquement** les nœuds modifiés. Ce détail est ce qui préserve le focus de l'input
en cours de saisie, la position de scroll, les classes CSS et les events sur les nœuds inchangés.

```
Phase 1 — render initial
Navigateur                       Serveur Symfony
    │── GET /ma-page ───────────────►│  instancie le composant
    │                                │  Twig render
    │                                │  sérialise l'état dans le DOM
    │◄── HTML complet ───────────────│
    │
    │  Le composant n'existe plus côté serveur.
    │  Son état est encodé dans le HTML.

Phase 2 — cycle interaction
Navigateur                       Serveur Symfony
    │  [clic ou input]               │
    │── POST /_components ──────────►│  reconstruit le composant
    │   { props, updated, action }   │  hydrate, exécute l'action
    │                                │  Twig re-render
    │                                │  re-sérialise l'état
    │◄── HTML partiel ───────────────│
    │
    │  morphdom patche les nœuds modifiés.
    │  Focus, scroll, inputs préservés.
```

Quatre conséquences directes pour le mental model d'un dev Symfony :

- **Aucun état implicite entre deux requêtes.** Une variable d'instance qui n'est pas une `LiveProp` est perdue à chaque cycle. Si ça doit persister, ça doit
  être une `LiveProp`.
- **Une `LiveProp writable`, c'est une entrée utilisateur.** À traiter comme un champ de formulaire, avec validation, contraintes, et zéro confiance par défaut.
- **Chaque action est un round-trip.** Le _debounce_ sur les inputs texte n'est pas un détail de polish, c'est une règle.
- **La taille de l'état sérialisé compte.** Une entité Doctrine entière dans une `LiveProp` est sérialisée à chaque cycle dans le DOM puis renvoyée à chaque
  POST. On stocke un ID et on recharge côté serveur — on y revient à l'épisode 4.

## Un Counter complet, en quinze lignes

Pour ancrer tout ça, le composant le plus minimaliste possible. Pas pour faire un tutoriel — pour montrer la surface réelle du code à écrire.

```php
// src/Twig/Components/Counter.php
use Symfony\UX\LiveComponent\Attribute\AsLiveComponent;
use Symfony\UX\LiveComponent\Attribute\LiveAction;
use Symfony\UX\LiveComponent\Attribute\LiveProp;
use Symfony\UX\LiveComponent\DefaultActionTrait;

#[AsLiveComponent]
final class Counter
{
    use DefaultActionTrait;

    #[LiveProp(writable: true)]
    public int $count = 0;

    #[LiveAction]
    public function increment(): void
    {
        ++$this->count;
    }
}
```

```twig
{# templates/components/Counter.html.twig #}
<div {{ attributes }}>
    <h2>Compteur : {{ count }}</h2>
    <button data-action="live#action" data-live-action-param="increment">+1</button>
</div>
```

Quatre détails cruciaux. `#[AsLiveComponent]` remplace `#[AsTwigComponent]` de l'épisode 2 — le couplage avec le socle est explicite. Le `DefaultActionTrait`
active le re-render même sans action explicite. `{{ attributes }}` injecte automatiquement `data-controller="live"`, l'état sérialisé des `LiveProp` et le token
CSRF — c'est ce qui rend le composant détectable et hydratable côté client. `data-action="live#action"` + `data-live-action-param` relie le clic du bouton à la
méthode `increment` côté PHP.

Au clic, on ouvre l'onglet Network, on observe un `POST /_components/Counter?action=increment` qui part. La réponse contient le HTML du composant re-rendu. Le
DOM est patché, le compteur s'incrémente, **focus et scroll préservés**. Aucune ligne de JavaScript écrite à la main.

## Une recherche live, avec debounce

Le pas suivant : un input de recherche qui filtre une liste de produits en direct, avec un debounce pour éviter de bombarder le serveur à chaque frappe.

```php
// src/Twig/Components/ProductSearch.php
#[AsLiveComponent]
final class ProductSearch
{
    use DefaultActionTrait;

    #[LiveProp(writable: true)]
    public string $query = '';

    public function __construct(private ProductRepository $products) {}

    public function getResults(): array
    {
        return strlen($this->query) >= 2
            ? $this->products->search($this->query)
            : [];
    }
}
```

```twig
{# templates/components/ProductSearch.html.twig #}
<div {{ attributes }}>
    <input type="search" data-model="debounce(300)|query" placeholder="Rechercher…">
    <ul>
        {% for product in computed.results %}
            <li>{{ product.name }}</li>
        {% endfor %}
    </ul>
</div>
```

Deux choses à noter. Le `data-model="debounce(300)|query"` lie l'input à la prop `query` mais ne déclenche le re-render qu'**après 300 ms d'inactivité de
frappe** — c'est ce qui fait passer d'une requête par caractère tapé à une requête par mot fini. La méthode `getResults()` est appelée via `computed.` côté
template (cf. épisode 2) pour ne pas exécuter deux fois la requête SQL si le bloc `{% for %}` est précédé d'un `{% if %}`.

À l'usage, on peut poser un breakpoint Xdebug dans `getResults()` et débugger normalement. Le profiler Symfony voit le `POST /_components/ProductSearch` comme
n'importe quelle requête. Aucun outil nouveau à apprendre.

## Anatomie d'un payload : ce qui voyage vraiment

À chaque interaction, le contrôleur Stimulus côté client construit un payload `POST /_components/<NomDuComposant>?action=<methode>` avec un corps JSON (ou
form-data selon la version) qui ressemble à ceci — _exemple illustratif, structure simplifiée_, à capturer sur ton projet pour la version exacte de ton bundle :

```json
{
  "props": {
    "query": "",
    "@attributes": { "id": "live-1630620926-0" },
    "@checksum": "rZqkfjCx6svzp7p1xYbt9lwLJ2IrEzLkUZC5n/EXj5Q="
  },
  "updated": {
    "query": "cl"
  }
}
```

`props` contient l'état sérialisé tel qu'il était au render précédent — les valeurs de chaque `LiveProp`. `updated` contient les valeurs modifiées côté client
depuis le dernier render — typiquement ce qui vient d'être tapé dans l'input lié par `data-model`. La clé `@checksum` est une **signature serveur** des props :
si un attaquant modifie une prop côté client (par exemple en passant une `LiveProp` non-writable de `"user"` à `"admin"` via les DevTools), la signature ne
correspond plus et le bundle refuse la requête. Les `LiveProp(writable: true)` sont les seules valeurs que le serveur accepte de voir bouger côté client — tout
le reste est immuable côté client par défaut.

C'est un point de sécurité qu'on retrouve à l'épisode 4 : la barrière n'est pas dans la vigilance du dev, elle est dans la convention du bundle.

## Quatre niveaux de puissance pour `LiveProp`

`LiveProp` n'est pas un simple toggle « synchronisé ou pas ». Le bundle expose quatre modes selon le besoin.

**Read-only par défaut.** `#[LiveProp]` sans option : la valeur persiste entre re-renders mais le client ne peut pas la modifier. C'est le mode pour des
constantes calculées au render initial (un `$max = 1000` qu'on veut garder identique entre deux cycles).

**Writable.** `#[LiveProp(writable: true)]` : modifiable depuis le client via `data-model`, déclenche un re-render. C'est le mode « input de recherche, filtre,
case à cocher ».

**Writable sélectif.** `#[LiveProp(writable: ['name', 'email'])]` sur une prop typée objet : seuls les champs listés sont exposés à l'écriture côté client.
C'est une whitelist explicite — on ne fait pas confiance à l'objet entier.

**URL binding.** `#[LiveProp(writable: true, url: true)]` : la valeur est reflétée dans la query string (`?sort=name`), ce qui rend la page **partageable par
URL**, gère le bouton retour du navigateur, et permet le bookmarking. Excellent pour les pages de filtre / tri / pagination.

Pour les objets complexes (entités Doctrine, value objects, DTOs), on peut surcharger l'hydratation et la déshydratation pour ne sérialiser qu'un ID :

```php
#[LiveProp(writable: true, hydrateWith: 'hydrateProduct', dehydrateWith: 'dehydrateProduct')]
public Product $product;

public function dehydrateProduct(Product $product): int
{
    return $product->getId();
}

public function hydrateProduct(int $id, ProductRepository $repo): Product
{
    return $repo->find($id) ?? throw new \RuntimeException('Product not found');
}
```

Sans cette surcharge, l'entité Doctrine entière serait sérialisée en JSON dans le DOM puis renvoyée à chaque cycle. C'est le piège perf le plus fréquent — on y
revient à l'épisode suivant.

## Ce qu'on n'écrit plus

Pour conclure cet épisode, le contraste qui rend le bénéfice tangible. Voici ce qu'on _arrête_ d'écrire dès qu'un fragment passe en Live Component.

| Sans Live Components                         | Avec Live Components            |
| -------------------------------------------- | ------------------------------- |
| Écrire un endpoint Ajax dédié                | **Aucun endpoint** à écrire     |
| Définir un format de réponse (JSON ? HTML ?) | **Du HTML**, c'est tout         |
| Réimplémenter la logique en JS               | La logique reste **en PHP**     |
| Mettre à jour le DOM à la main               | **DOM morphing** automatique    |
| Gérer CSRF, signature, sérialisation         | **Géré par le bundle**          |
| Tester deux codebases (PHPUnit + Jest)       | **PHPUnit suffit** (épisode 4)  |

Ce n'est pas l'absence de JavaScript qui fait le bénéfice — c'est l'absence du _couple_ JS custom + endpoint custom + format custom + tests custom à maintenir
en parallèle de la version PHP. On garde Symfony, on gagne l'interactivité, on laisse la complexité SPA de côté pour les zones qui en ont réellement besoin.

Reste à répondre aux trois questions que la prod pose toujours : comment on teste ça sans navigateur, comment on profile une app qui en est truffée, et comment
on sécurise un objet dont l'état voyage dans le DOM. C'est l'objet de l'[épisode 4](/blog/live-components-tester-profiler-securiser/).
